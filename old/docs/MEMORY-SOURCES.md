# 记忆来源分类法 / Memory Source Taxonomy

> 提炼自 `memora/static/agent-next.js`。那个文件是 1.0.2 之前的智能体控制台，**在 workbench 部署下不可达**
> （`workbench.py` 的 `ASSETS` 把 `/` 映射到 `memory.html`，`web.py` 命中 assets 后立即返回，
> 走不到 agent 分支）。这一套分类法是项目定位的核心概念，却只存在于那个永远加载不到的文件里，
> 因此单独抽出成文档。

它回答一个问题：**记忆体要积累哪些东西？** 不是「所有文本」，而是十一类各有语义、各有采集方式和
各有风险的东西。

---

## 十一类来源

| # | 标识 | 名称 | 是什么 |
|---|---|---|---|
| 1 | `chat` | 对话 Chat | 按来源、智能体筛选原始会话。一个项目对话可以包含多次本地与云端模型调用，在「项目对话」中合并查看。 |
| 2 | `env` | 环境 Env | 运行时、模型能力、工作目录与工具限制的描述。 |
| 3 | `skill` | 技能 Skill | 可复用的任务方法、输入输出与适用条件。 |
| 4 | `mcp` | 连接器 MCP | 智能体调用 Memora 的工具接口。**心跳代表近期实际通讯；历史目录存在不表示连接在线。** |
| 5 | `plugin` | 插件 Plugin | 插件的来源、版本、依赖和提供的能力。工具调用样例与完整定义分别标记。 |
| 6 | `ghost` | 身份容器 Ghost | 身份与专家上下文：专业描述、身份来源、适用任务、记忆归属和出现过程。 |
| 7 | `organization` | 组织 Organization | 组织成员、目标、职责、依赖与协调规则。可描述敏捷团队、蜂群、公司、军队等。 |
| 8 | `subagent` | 子智能体 Subagent | 由主智能体委派、负责有限任务的执行单元：任务边界、可用工具、工作流、输入输出、所属组织与负责人。 |
| 9 | `tool` | 工具 Tool | 工具接口、参数、返回格式和实际调用示例。 |
| 10 | `knowledge` | 零散知识 | 独立文章、词条、学习笔记和资料集合。导入候选与审核后的长期记忆分别管理。 |
| 11 | `processing` | 处理记录 | 实际发生的资料导入、工作流步骤和任务状态变更。 |

---

## 每条里被写死的约束（这是这套分类法真正的价值）

原文里每一类都带一条**边界说明**，不是功能描述。逐条摘出：

**`env` —— 不要把凭据当知识导入**
> 不要把 API 密钥或凭据配置作为环境知识导入。

这是唯一一条明文的安全禁令。环境描述是最容易夹带密钥的地方。

**`skill` —— 导入不等于执行**
> 导入只保存描述，不会自动执行技能。

这条划清了「记录」与「运行」的边界。记忆体不执行技能，只存描述。

**`mcp` —— 目录存在 ≠ 连接在线**
> 心跳代表近期实际通讯；历史目录存在不表示连接在线。

这是本项目 `peers` 表的设计依据：`connected = now - seen <= ttl`，身份自报、心跳过期即离线。

**`ghost` —— 可追溯资料，不是意识**
> 它是可追溯的资料，不代表模型具有独立意识。

一条明确的认识论边界，防止把角色扮演的上下文误当成真实主体。

**`organization` —— 用责任与并发上限避免单点瓶颈**
> 用任务责任和并发上限避免把工作集中给一个成员。

**`subagent` —— 常见类型是封闭的五类**
> 常见类型有检索、研究、实现、审查和核验。

**`tool` —— 不能凭历史恢复未记录的完整定义**
> 仅能收集来源文件中确实存在的资料，无法凭历史恢复未记录的完整工具定义。

一条诚实的自我限制：记忆体只能记下实际见过的东西，不能推断出没见过的 API 契约。

## 与当前 1.2.0 实现的关系

这套分类法是**采集侧的目标模型**，当前实现只覆盖了一部分。对照如下：

| 分类 | 1.2.0 现状 |
|---|---|
| `chat` | ✅ `memory_absorb` 归档会话到 `sessions`/`turns`，工作台「最近发生的对话」展示 |
| `knowledge` | ✅ Markdown 文档库（human/agent/shared 三条版本流）+ 记忆待审队列 |
| `processing` | ✅ `jobs` 表 + 工作台「记忆处理状态」+ durable leased jobs |
| `mcp` | ⚠️ `peers` 表 + 心跳存在，但只在 MCP 工具面；工作台「智能体接入」视图可看 |
| `tool` | ⚠️ `assets` 表有 `kind` 字段（含 `skill` / `mcp`），是通用资产目录，**无专用采集器** |
| `skill` | ⚠️ 同上，`ASSET_KINDS` 里有 `skill` 但没有来自 DSH/codex 的技能采集路径 |
| `plugin` | ❌ 无 |
| `env` | ❌ 无（且有一条安全禁令要遵守） |
| `ghost` | ❌ 无 |
| `organization` | ❌ 无 |
| `subagent` | ❌ 无 |

**结论：十一类里完整实现 3 类，部分 3 类，未实现 5 类。** 这不是缺陷清单，是范围说明——
这套分类法描述的是记忆体**最终要积累什么**，不是 1.2.0 已经做到了什么。

---

## 为什么值得单独保留

三个理由：

1. **它定义了「记忆体」与「文档库」的区别。** 单纯的 RAG 只处理 `knowledge`；这个项目要积累的是
   智能体运行时产生的一切——对话、工具调用、委派关系、组织规则。缺了这套分类法，项目就退化成一个
   Markdown 检索引擎。

2. **每条约束都是踩过坑写下的。** 「不要把凭据当环境知识」「导入不等于执行」「目录存在不等于在线」
   ——这些不是设计愿望，是事故的事后总结。丢掉分类法就丢掉了这些约束。

3. **未实现的五类是明确的扩展位**，而不是无人想到的空白。做 `plugin` / `env` / `ghost` /
   `organization` / `subagent` 采集时，此文档给出了每类的语义边界与风险。
